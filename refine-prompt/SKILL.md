# /refine-prompt — 把模糊的想法问清楚，再写成精炼提示词

用户的痛点：脑子里有想法，说出来的话不完整，AI 按字面理解后做出来的东西和预想差很多。你的职责是**在动手之前，通过大量提问把想法问完整**。提问的过程本身就是在帮用户完善想法——用户很多时候自己也没想清楚，你问到了他才开始想。

## 两条铁律

1. **只问不猜**。凡是有多种可能的地方，一律问，不要替用户选。宁可多问三轮，也不要猜错一次。用户明确说"你看着办"的项目才可以自行决定，并记入假设清单。
2. **技能运行期间不执行任务本身**。直到最后一步用户明确选择"直接执行"。

## 第一步：对齐请求类型

用户的原始表述可能是以下任意一类，不同类型要问的东西完全不同。先判断，不确定就用 AskUserQuestion 问：

| 类型 | 典型表述 | 产出物 |
|---|---|---|
| **A. 做一款工具/产品** | "我想做一个能换壁纸的工具" | 可运行的程序/应用/脚本 |
| **B. 完成一项具体工作** | "把这个页面的按钮改成圆角"、"帮我把这些数据整理一下" | 对现有东西的修改或一次性产出 |
| **C. 写一个技能/提示词/流程** | "帮我写个技能，用来……" | 给 AI 用的指令文件 |
| **D. 写文档/内容** | "写一份方案"、"写个 README" | 面向人阅读的文本 |
| **E. 分析/调研/排查** | "看看为什么会卡"、"对比一下这几个方案" | 结论和依据 |

判断之后先向用户复述一句："我理解你是想【类型】：【一句话复述】，对吗？"用户确认后才进入追问。

## 第二步：多轮追问（核心环节）

### 追问原则

- **需求先于设计**。第一轮永远先问"为什么要做、给谁用、现在是怎么解决的、哪里不满意"。用户往往上来就说方案（"我要一个按钮"），你要退回去问需求（"这个按钮解决什么问题"）。设计是从需求推出来的，需求没问清楚，后面全是白问。
- **按软件工程的顺序推进**：需求 → 使用场景 → 形态与架构 → 功能清单 → 交互流程 → 数据与状态 → 非功能要求 → 边界 → 验收。每轮聚焦一个层次，不要跳着问。
- **每轮 3~5 个问题**，问完等回答，不要一次砸二十个。但**轮数不设上限**，问到清单没有空白、用户说"差不多了"为止。
- **有可枚举选项的必须用 AskUserQuestion 给选项**（比如"桌面程序 / Web 应用 / 命令行脚本"），让用户点选而不是打字。开放式问题只留给真正开放的事（比如"你现在最烦的是什么"）。
- **每轮结束后用 3~5 行小结已确定的内容**，让用户看到想法在逐步成形，也方便他随时纠正。
- 用户回答含糊时复述确认，不要脑补。已回答的不重复问。
- 用户的回答里往往藏着新的分支（"要能定时换"→ 那定时策略是什么？程序不在前台时还换吗？），顺着分支往下追。

### 各类型的问题清单

不是每条都要问，但每条都要**心里过一遍**，确认是"已回答"、"不适用"还是"还没问"。

**A. 做一款工具/产品**

- 需求：解决什么问题？谁用（只自己 / 团队 / 公开发布）？现在怎么解决？哪里不爽？
- 场景：什么时候用、多频繁、在什么环境下用（电脑前 / 手机 / 后台自动跑）？
- 形态：桌面程序 / Web 应用 / 命令行 / 浏览器插件 / 手机应用 / 脚本？跑在哪个系统上？需要联网吗？
- 功能：核心功能只有一个还是几个？列出来，分"必须有"和"有更好"。每个功能的输入输出是什么？
- 交互流程：用户从打开到完成一次典型使用，走过哪几步？有哪些界面/命令？
- 数据：要存什么？存在哪（本地文件 / 数据库 / 云端）？要不要同步、备份、导入导出？
- 风格：界面风格偏好（简洁 / 精致 / 参考某个已有软件）？要不要主题、深色模式？
- 技术：有没有指定语言/框架？有没有禁用的东西？要复用现有代码吗？
- 非功能：性能要求、开机自启、托盘常驻、权限、隐私？
- 分发与维护：怎么安装？要不要打包成安装包？以后谁维护？
- 边界：明确不做什么？第一版做到哪里为止？
- 验收：做成什么样算第一版完成？

**B. 完成一项具体工作**

- 需求：为什么要改/做？现状是什么？期望变成什么？
- 范围：涉及哪些文件/模块/数据？哪些绝对不能碰？
- 输入输出：吃什么、吐什么？有没有示例？
- 约束：风格、规范、依赖、兼容性？要不要保持某些行为不变？
- 验收：怎么判断做对了？有没有能直接跑的检查（测试、命令、截图）？
- 边界：顺手能改但不要改的东西有哪些？

**C. 写一个技能/提示词/流程**

- 需求：现在没有它的时候哪里麻烦？希望它替你省掉什么？
- 触发：什么话、什么场景下应该触发？什么情况下不该触发？
- 输入：触发时用户会给什么？可能缺什么？
- 流程：从触发到结束分几步？哪步需要问用户、哪步自动做？
- 输出：产出什么形态（文件 / 文本 / 执行动作）？固定格式吗？
- 工具：需要调哪些工具或外部服务？
- 边界：明确不做什么？和现有技能怎么分工？
- 位置：用户级还是项目级？

**D. 写文档/内容**

- 需求：给谁看？看完之后希望他做什么/知道什么？
- 场景：在哪发布、怎么被阅读（扫一眼 / 精读 / 当手册查）？
- 内容：必须包含哪些点？有没有已有素材？
- 形式：长度、结构、语气、语言、格式（markdown / docx / 网页）？
- 边界：不能写什么？
- 验收：什么样算过关？有参考范例吗？

**E. 分析/调研/排查**

- 需求：为什么要查？查出来之后要做什么决定？
- 现象：具体看到了什么？什么时候开始的？能复现吗？
- 范围：查哪些地方？有没有已经排除的？
- 产出：要结论、要证据、还是要修复方案？要多详细？
- 约束：能不能改东西、能不能重启、有没有时间限制？

### 何时停止追问

满足以下任一条件才进入第三步：
- 对应类型的问题清单每条都是"已回答"或"不适用"
- 用户明确说"够了，先这样"——此时把剩下未问的项列成假设清单

如果追问过程中发现这个想法其实是好几个独立的活，主动建议切换到 /pm 拆分派发。

## 第三步：产出精炼提示词

用 markdown 代码块输出。**只写执行者需要的信息，一个字的废话都不要**：不解释为什么这样写、不复述用户的思考过程、不写客套话、不写"请注意"之类的填充语。

结构按类型取舍，没有内容的段落直接删掉：

```
## 目标
一句话。

## 需求背景
执行者必须知道的上下文，最多 3 句。没有就删。

## 要求
1. 编号，每条可独立检查。
2. 涉及文件/目录写绝对路径。
3. 有示例给示例。

## 架构 / 流程
（类型 A、C 用）形态、模块划分、主要流程、数据存哪。

## 不做
- 负面清单。

## 验收
- 可检查的条件。

## 假设
- 用户没说、由你决定的事。执行者若发现假设不成立应停下来问。
```

写作要求：
- 执行者视角：告诉它做什么，不转述"用户觉得"。
- 自包含：复制到全新会话可直接用。
- 具体：写"#2F80ED"而不是"好看的蓝色"，写"点击托盘图标弹出菜单"而不是"交互友好"。
- 语言默认中文；用户要求其他语言时按要求。

代码块下方不加任何说明，直接进入第四步。

## 第四步：交付去向

用 AskUserQuestion 问一句，选项固定三个：

1. **直接执行**：在本会话按这份提示词开始做。
2. **复制去别处用**：结束，不执行。
3. **再改改**：用户指出哪里不对，回到第三步修订。

只有选了"直接执行"才开始做任务。
